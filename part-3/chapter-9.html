AWS: The Giant Supermarket in the Sky

Rent any computing resource in the world, on-demand, in seconds.

What you'll learn in this chapter

  • Why cloud computing exists and the problem it solves for every company on earth
  • AWS's 200+ services, organized into categories you can actually remember
  • EC2 — launching and connecting to a virtual machine in the cloud
  • S3 — the infinitely scalable file storage bucket the entire internet uses
  • IAM — the security system that controls who can touch what
  • VPC — your private network inside AWS's data centers
  • RDS — a managed database so you never have to install Postgres yourself again
  • Lambda — running code without owning a single server
  • CloudWatch — monitoring everything that matters

The Supermarket Analogy

Imagine you decide to cook a big dinner for 200 guests. You could go the old-fashioned route: buy your own refrigerator, your own industrial oven, your own plates, build a pantry stocked with every possible ingredient, and then figure out what to do with all that equipment when the dinner is over and nobody needs it anymore. Or — you could use a giant supermarket that already has everything, fully stocked, where you pay only for what you take off the shelf.

That is exactly what AWS is. AWS (Amazon Web Services) is the world's largest technology supermarket. Need a server? Rent one. Need a database? Rent one. Need to store a million files? Rent the storage. Need ten thousand servers for Black Friday and zero servers in January? Rent ten thousand, then return them. Pay by the hour, sometimes by the second.

The story of how AWS was born is fascinating. Amazon the retailer had to build a massive internal infrastructure to handle their own e-commerce operations. They got very good at building reliable, scalable computing systems. Around 2003, some engineers asked: what if we rented this infrastructure to other companies? In 2006, AWS launched publicly — and accidentally created the cloud computing industry. Today AWS powers roughly a third of the entire internet, including Netflix, Airbnb, NASA, the CIA, and thousands of startups.

🛒 The Supermarket Analogy

Before AWS: every company bought their own servers, hired IT staff to manage them, paid electricity bills, and scrambled when traffic spiked. If you needed 100 servers, you bought 100 — even if you used 10 most of the time and needed 100 only twice a year.

After AWS: rent exactly what you need, exactly when you need it. Scale up in minutes. Scale down in minutes. Pay only for actual usage. No upfront cost. No idle hardware. No data center lease.

Why Cloud Computing Exists

Before the cloud, every company that needed servers went through the same painful ritual. First, you estimated how much computing power your application would ever need — which is essentially impossible to predict accurately. Then you ordered physical servers, which took weeks to arrive. Then you hired people to rack them in a data center, wire them up, install the operating system, and configure the network. Then you paid rent for the data center space, paid for electricity to run the servers and more electricity to cool them, and hoped you guessed right about how much capacity you'd need.

If your traffic doubled unexpectedly — say, a celebrity tweeted about your product — you were stuck. Your servers were already at capacity, and getting more would take weeks. If your traffic halved — say, you lost a big customer — your paid-for servers sat idle, burning money doing nothing. The economics were brutal and the operational overhead was enormous.

Cloud computing flipped this completely. The cloud providers — AWS, Google, Microsoft — built enormous data centers stuffed with hardware. They buy at such scale they get hardware cheaper than any single company could. Then they rent it out, charging a premium over their costs but still far cheaper than owning equivalent hardware. Everyone wins: the cloud provider makes money, and the customer gets cheaper, more flexible infrastructure.

📚 Key Terms: Cloud Computing

IaaS (Infrastructure as a Service): rent raw virtual machines and networking. You manage the OS and up. Example: EC2.

PaaS (Platform as a Service): rent a managed platform — you just deploy code. Example: AWS Elastic Beanstalk, Heroku.

SaaS (Software as a Service): rent fully finished software. Example: Gmail, Salesforce.

Serverless: run code without thinking about servers at all. Pay per execution. Example: AWS Lambda.

🤯 Fun Fact: AWS Free Tier

AWS offers a genuinely useful free tier: 750 hours/month of t3.micro EC2 instances (enough to run one server 24/7 for a year), 5GB of S3 storage, 1 million Lambda invocations per month, and a 750-hour free RDS instance. A complete side project can run on AWS for free for 12 months — and some services (like Lambda's free tier) never expire.

EC2 — Your Virtual Machine in the Cloud

EC2 (Elastic Compute Cloud) is the original AWS service. It gives you virtual machines — called instances — running in AWS's data centers. You pick the operating system, the size, the region, and you have a full Linux (or Windows) machine to SSH into and do whatever you want with.

Think of an EC2 instance like renting a complete computer at a coffee shop — except the coffee shop has locations in 30 countries, the computer can be any size from a tiny netbook to a machine with 192 CPU cores and 24TB of RAM, and you pay by the second.

Instance Types

EC2 instance types follow a naming pattern: family.size. The family describes what the machine is optimized for; the size describes how big it is. 

Instance Name Anatomy:   t3.medium
                         ││ │└──── size: nano/micro/small/medium/large/xlarge/2xlarge...
                         ││ └───── generation: 3rd gen t-family
                         │└─────── family: t = general purpose burstable
                         └──────── (all families below)

Common Families:
  t3, t4g   → General purpose, burstable (cheap, good for variable workloads)
  m6i, m7g  → General purpose, balanced (steady workloads)
  c6i, c7g  → Compute optimized (high CPU: web servers, batch jobs)
  r6i, r7g  → Memory optimized (databases, caches: high RAM)
  g4dn, p3  → GPU instances (machine learning, video processing)
  i3        → Storage optimized (fast NVMe disks)

Common Sizes and Specs (t3 family):
  t3.nano      0.5 GB RAM   2 vCPU   ~$0.005/hr
  t3.micro     1 GB RAM     2 vCPU   ~$0.010/hr  ← Free Tier eligible

  t3.large     8 GB RAM     2 vCPU   ~$0.083/hr

  t3.2xlarge   32 GB RAM    8 vCPU   ~$0.333/hr

Key EC2 Concepts

Before launching an instance, you need to understand four things:

  • AMI (Amazon Machine Image): the pre-baked OS snapshot you start from. Think of it as the template. Amazon Linux 2023, Ubuntu 22.04, and Windows Server 2022 are popular choices. Thousands of community AMIs exist for pre-configured stacks.
  • Key Pairs: SSH keys. AWS stores your public key; you keep the private key (.pem file). You need it to SSH into your instance. Lose it and you're locked out.
  • Security Groups: virtual firewalls. You define which ports are open to which IP ranges. By default, everything is blocked. You explicitly allow SSH (port 22), HTTP (80), HTTPS (443), etc.
  • Elastic IP: a static public IP address that doesn't change when you stop and restart your instance. By default, your instance gets a new IP every time it restarts.

Launching an Instance with the AWS CLI

The AWS CLI is the command-line interface for all AWS services. Install it with pip install awscli or download from aws.amazon.com/cli. Configure it with aws configure (you'll need your Access Key ID and Secret Access Key from IAM). 

# Launch an EC2 instance
aws ec2 run-instances \
  --image-id ami-0c55b159cbfafe1f0 \
  --instance-type t3.micro \
  --key-name my-key \
  --security-group-ids sg-12345678 \
  --subnet-id subnet-12345678 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=my-server}]'

# List all running instances in a readable table
aws ec2 describe-instances \
  --query 'Reservations[*].Instances[*].[InstanceId,State.Name,PublicIpAddress,Tags[?Key==`Name`].Value|[0]]' \
  --output table

# Stop an instance
aws ec2 stop-instances --instance-ids i-0abc12345def67890

# Start it again
aws ec2 start-instances --instance-ids i-0abc12345def67890

# Terminate (permanently destroy) an instance
aws ec2 terminate-instances --instance-ids i-0abc12345def67890

# SSH into your running instance
# (chmod 400 protects the key file — SSH refuses to use world-readable keys)
chmod 400 my-key.pem
ssh -i my-key.pem ec2-user@52.10.20.30

# Allocate an Elastic IP and associate it with your instance
aws ec2 allocate-address --domain vpc
aws ec2 associate-address \
  --instance-id i-0abc12345def67890 \
  --public-ip 54.200.100.10
💡 Tip: Use User Data to Bootstrap Your Server

The --user-data flag lets you pass a shell script that runs automatically when your instance first boots. This is how you install Nginx, Docker, or your app without SSHing in manually. Pass a file with --user-data file://setup.sh. The script runs as root on first boot.

S3 — Infinitely Scalable File Storage

S3 (Simple Storage Service) is one of the most brilliant pieces of infrastructure ever built. It stores objects — any file, any size up to 5TB — inside containers called buckets. There is no limit to how many objects you can store. S3 automatically replicates your data across multiple data centers in a region, giving you 99.999999999% (eleven nines) durability. In practical terms: the chance of losing a file stored in S3 is essentially zero.

S3 is used for everything: serving static websites, storing user profile photos, archiving log files, distributing software builds, hosting Docker layer caches, storing Terraform state files, and delivering video assets through CloudFront. If something needs to be stored and retrieved, S3 is usually the answer.

Bucket names must be globally unique across all AWS accounts. Think of buckets like domain names — there's only one my-app-uploads in the world. 

# Create a bucket (name must be globally unique)
aws s3 mb s3://my-unique-bucket-name-2024

# Upload a single file
aws s3 cp photo.jpg s3://my-bucket/uploads/

# Upload an entire directory (sync — only copies changed files)
aws s3 sync ./dist/ s3://my-bucket/ --delete

# Download a file
aws s3 cp s3://my-bucket/uploads/photo.jpg ./local-photo.jpg

# List all objects in a bucket
aws s3 ls s3://my-bucket/ --recursive --human-readable

# Make a specific file publicly readable
aws s3api put-object-acl \
  --bucket my-bucket \
  --key uploads/photo.jpg \
  --acl public-read

# Enable static website hosting on a bucket
aws s3 website s3://my-bucket \
  --index-document index.html \
  --error-document 404.html

# Set a lifecycle policy to auto-delete old files after 30 days
aws s3api put-bucket-lifecycle-configuration \
  --bucket my-bucket \
  --lifecycle-configuration file://lifecycle.json

# Generate a pre-signed URL (temporary access link, expires in 1 hour)
aws s3 presign s3://my-bucket/secret-report.pdf --expires-in 3600
📚 Key Term: S3 Storage Classes

S3 has multiple storage classes at different price points: Standard — fast, expensive, frequently accessed data; Standard-IA (Infrequent Access) — cheaper, slightly slower retrieval, for data you access a few times a month; Glacier — very cheap archive storage, takes minutes to hours to retrieve. You can set lifecycle policies to automatically move objects between classes as they age.

IAM — Who Can Do What

IAM (Identity and Access Management) is the security backbone of every AWS account. Before a single AWS API call succeeds, IAM checks: "Is this entity allowed to do this thing on this resource?" Every access request — from your CLI, from a Lambda function, from an EC2 instance — goes through IAM.

Think of IAM like a hotel key card system. Every person (user) or machine (role) gets a key card. The key card only opens certain doors. The security manager (IAM) decides which doors each card can open. The golden rule: give each card access to only the doors it actually needs — nothing more. This is called the principle of least privilege.

The Four IAM Building Blocks

  • Users: individual human beings or service accounts with long-term credentials (access key + secret key). Use IAM users for humans who need console or CLI access.
  • Roles: not credentials — a role is a set of permissions that a resource assumes temporarily. An EC2 instance assumes a role to call S3. A Lambda function assumes a role to write to DynamoDB. Roles are safer than users for machine-to-machine access because the credentials rotate automatically.
  • Policies: JSON documents that define permissions. A policy says: allow or deny this action on this resource. Attach policies to users, roles, or groups.
  • Groups: collections of users who share the same policies. Instead of attaching the same policy to 20 developers individually, attach it to a "Developers" group and add them all.
⚠️ Never Use Root Credentials

When you first create an AWS account, you have root credentials — an email/password combination that can do literally anything to your account, including deleting everything and racking up a $50,000 bill. Lock root credentials away immediately. Enable MFA on root. Create an IAM admin user for daily work. Never use root credentials for programmatic access.

Writing an IAM Policy

Policies are JSON. Each policy contains statements. Each statement has an Effect (Allow or Deny), one or more Actions (what API calls), and one or more Resources (what specific AWS resources). Here is a minimal policy granting read-only access to one specific S3 bucket: 

// IAM Policy: read-only access to a specific S3 bucket
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-app-bucket",
        "arn:aws:s3:::my-app-bucket/*"
      ]
    }
  ]
}

The ARN (Amazon Resource Name) is the unique identifier for every resource in AWS. The pattern is arn:partition:service:region:account-id:resource. The first ARN targets the bucket itself (needed for ListBucket); the second targets all objects inside it (needed for GetObject). 

# Create a policy from a JSON file
aws iam create-policy \
  --policy-name S3ReadOnlyMyBucket \
  --policy-document file://policy.json

# Attach the policy to a role
aws iam attach-role-policy \
  --role-name my-app-role \
  --policy-arn arn:aws:iam::123456789012:policy/S3ReadOnlyMyBucket

# Create an IAM user
aws iam create-user --user-name alice

# Create CLI access keys for a user
aws iam create-access-key --user-name alice

VPC — Your Private Network

By default, every AWS resource you create goes into a default VPC (Virtual Private Cloud) — a private network that AWS sets up for you automatically. But for production systems, you should design your own VPC from scratch.

Think of a VPC as a private office building on AWS's campus. The building has its own address range. Only resources inside the building can talk to each other directly. Certain doors (gateways) connect the building to the outside world. You decide which floors (subnets) are accessible from the street and which floors are internal-only. 

Your VPC  (10.0.0.0/16 — 65,536 private IP addresses)
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Public Subnet (10.0.1.0/24)    Private Subnet (10.0.2.0/24)│
│  ┌─────────────────────────┐    ┌──────────────────────────┐│
│  │  Load Balancer          │    │  App Server (EC2)        ││
│  │  Bastion Host (SSH)     │    │  Database (RDS)          ││
│  │  NAT Gateway            │    │  (no direct internet)    ││
│  └───────────┬─────────────┘    └──────────────────────────┘│
│              │                                              │
└──────────────┼──────────────────────────────────────────────┘
               │
        Internet Gateway
               │
           The Internet

Key VPC concepts you must know:

  • Subnets: subdivisions of your VPC's IP range. Public subnets have a route to the Internet Gateway. Private subnets don't — traffic can only come from within the VPC or through the NAT Gateway.
  • Internet Gateway: the door between your VPC and the public internet. Without it, nothing can reach the internet.
  • NAT Gateway: allows resources in private subnets to initiate outbound connections to the internet (to download updates, call external APIs) without being reachable from the internet.
  • Route Tables: rules that say "traffic destined for X goes via Y." Public subnets have a route sending internet-bound traffic through the Internet Gateway. Private subnets route internet-bound traffic through the NAT Gateway.
  • Security Groups: stateful firewalls attached to individual resources. Think of them as a bodyguard for each server.
  • NACLs (Network ACLs): stateless firewalls applied at the subnet level. Blunter and faster than Security Groups.

RDS — Your Managed Database

Running a production database is hard. You need automated backups, point-in-time recovery, failover to a standby when the primary crashes, security patching, performance monitoring, and careful storage management. RDS (Relational Database Service) handles all of that for you. You just connect to it with a standard connection string.

RDS supports PostgreSQL, MySQL, MariaDB, Oracle, and SQL Server. For most new projects, use PostgreSQL on RDS — it's the industry standard for relational data. If you want better performance and AWS-native features, look at Aurora (AWS's own PostgreSQL-compatible engine with up to 5x the throughput of standard RDS Postgres). 

# Create an RDS PostgreSQL instance
aws rds create-db-instance \
  --db-instance-identifier myapp-db \
  --db-instance-class db.t3.micro \
  --engine postgres \
  --engine-version "15.4" \
  --master-username admin \
  --master-user-password "SuperSecret123!" \
  --allocated-storage 20 \
  --db-subnet-group-name my-db-subnet-group \
  --vpc-security-group-ids sg-12345678 \
  --backup-retention-period 7 \
  --no-publicly-accessible

# Wait until the instance is available
aws rds wait db-instance-available \
  --db-instance-identifier myapp-db

# Get the endpoint to connect to
aws rds describe-db-instances \
  --db-instance-identifier myapp-db \
  --query 'DBInstances[0].Endpoint.Address' \
  --output text

# Create a snapshot (manual backup)
aws rds create-db-snapshot \
  --db-instance-identifier myapp-db \
  --db-snapshot-identifier myapp-db-snapshot-2024-01-15
💡 Tip: Place RDS in a Private Subnet

Your RDS instance should never be publicly accessible. Place it in a private subnet where only your application servers (in the same VPC) can connect to it. Access it from your local machine via an SSH tunnel through a bastion host, or use AWS Systems Manager Session Manager for secure access without opening port 22.

Lambda — Serverless Code Execution

Lambda is one of the most transformative ideas in cloud computing. The concept is simple: you give AWS a function (a piece of code). AWS runs it whenever a trigger fires — an HTTP request via API Gateway, an S3 file upload, a DynamoDB record change, a cron schedule. You pay per execution and per 100ms of execution time. When no triggers fire, you pay nothing. There is no server to provision, no OS to patch, no idle compute to pay for.

Think of Lambda like a vending machine. You put in a coin (an event), the machine runs for a moment, and gives you a result. The machine doesn't run between uses. You pay per use, not per hour you own the machine. 

// Lambda function: Node.js 20 — simple HTTP handler
export const handler = async (event) => {
  const name = event.queryStringParameters?.name || 'World';
  const region = process.env.AWS_REGION;

  return {
    statusCode: 200,
    headers: {
      'Content-Type': 'application/json',
      'X-Region': region
    },
    body: JSON.stringify({
      message: `Hello, ${name}!`,
      timestamp: new Date().toISOString()
    })
  };
};
# Create a Lambda function from a zip file
zip function.zip index.mjs

aws lambda create-function \
  --function-name hello-api \
  --runtime nodejs20.x \
  --role arn:aws:iam::123456789012:role/lambda-execution-role \
  --handler index.handler \
  --zip-file fileb://function.zip \
  --timeout 30 \
  --memory-size 256

# Update the function code
aws lambda update-function-code \
  --function-name hello-api \
  --zip-file fileb://function.zip

# Invoke the function manually
aws lambda invoke \
  --function-name hello-api \
  --payload '{"queryStringParameters": {"name": "AWS"}}' \
  response.json

# View recent logs
aws logs tail /aws/lambda/hello-api --follow
📚 Key Term: Cold Start

When a Lambda function hasn't run recently, AWS needs to spin up a container for it — this takes 100–500ms extra. This is called a cold start. For latency-sensitive apps, you can use Provisioned Concurrency to keep containers pre-warmed. For most workloads, cold starts are not a practical problem.

CloudWatch — Monitoring Everything

If AWS is the supermarket, CloudWatch is the security system, inventory tracker, and analytics dashboard all in one. Every AWS service sends data to CloudWatch automatically. EC2 sends CPU usage, memory, disk I/O. RDS sends database connections, query latency. Lambda sends invocation count, error rate, duration. You can also send your own custom metrics and logs from application code. 

# Create a CloudWatch alarm: alert when CPU exceeds 80% for 5 minutes
aws cloudwatch put-metric-alarm \
  --alarm-name HighCPUAlert \
  --metric-name CPUUtilization \
  --namespace AWS/EC2 \
  --statistic Average \
  --period 300 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 1 \
  --dimensions Name=InstanceId,Value=i-0abc12345def67890 \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:alerts-topic \
  --alarm-description "EC2 CPU too high — check the server"

# Create a log group
aws logs create-log-group --log-group-name /myapp/production

# Set log retention to 30 days (prevent unbounded cost)
aws logs put-retention-policy \
  --log-group-name /myapp/production \
  --retention-in-days 30

# Tail logs in real time (like `tail -f` but for CloudWatch)
aws logs tail /myapp/production --follow

# Query logs using CloudWatch Logs Insights
aws logs start-query \
  --log-group-name /myapp/production \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-string 'fields @timestamp, @message | filter @message like /ERROR/ | limit 50'
💡 Tip: Set Log Retention Periods

CloudWatch Logs never expire by default. If you forget to set a retention policy and your app logs 10GB/day, you'll eventually have a surprisingly large bill. Always set --retention-in-days when creating log groups. 30 days is a good default for application logs; 7 days for debug/trace logs.

Putting It All Together: A Typical AWS Architecture

Here is what a production-ready web application on AWS looks like. This is not over-engineering — it's the sensible minimum for anything with real users:

      │
      ▼

      │
      ▼

      │
      ▼

      │
      ├──▶ ECS/EC2 App Servers (in Private Subnet)

      │         │         └── RDS Read Replica (for read-heavy queries)

      │
      └──▶ S3 (static assets: images, JS, CSS)

All EC2/ECS instances have IAM Roles (no hardcoded credentials)
All resources in a custom VPC (public + private subnets)
CloudWatch collects all logs and metrics

Chapter Summary

  • AWS is the world's largest cloud provider — rent any infrastructure on demand, pay per use, scale in seconds.
  • AWS has 200+ services organized into Compute, Storage, Database, Networking, DevOps, Security, and Monitoring families.
  • EC2 provides virtual machines; choose an instance type based on your workload (t3 for general purpose, c6i for CPU-heavy, r6i for memory-heavy).
  • S3 is infinitely scalable object storage with 11 nines of durability — the backbone of most AWS architectures.
  • IAM controls all access in AWS. Use roles for machines, users for humans, groups for teams. Always apply least privilege.
  • VPC gives you a private network with public and private subnets, controlled internet access, and security groups as firewalls.
  • RDS provides managed databases — PostgreSQL, MySQL, MariaDB — with automatic backups, failover, and patching.
  • Lambda lets you run code without servers, triggered by events, billed per execution.
  • CloudWatch collects metrics, logs, and alarms for everything in your AWS account.
