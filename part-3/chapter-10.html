GCP & Azure: More Cloud Kingdoms

The other giants — and when to choose them.

What you'll learn in this chapter

  • The personality and strengths of each of the three major clouds
  • GCP's core services and how they map to AWS equivalents
  • Cloud Run — the easiest way to deploy a container on any cloud
  • GKE — why Google's managed Kubernetes is arguably the best
  • Azure's core services and Microsoft ecosystem advantages
  • Azure App Service — deploying web apps the Microsoft way
  • A practical framework for choosing between AWS, GCP, and Azure
  • Multi-cloud reality: why large companies use all three

The Three Kingdoms Analogy

Imagine three medieval kingdoms, each powerful, each ruling different territories, each built by people with different priorities and different visions of what a kingdom should be.

AWS is the oldest kingdom — built by merchants who needed to manage enormous warehouses and decided to rent them out. Over 18 years, they built a shop for absolutely everything. The market is overwhelming. The selection is unmatched. Most developers in the world have set foot in this market. It is the default.

GCP (Google Cloud Platform) is the kingdom of scholars and engineers. Built on the same infrastructure that runs Google Search, Gmail, YouTube, and Google Maps — systems that process more data per day than most companies will ever see in their lifetime. GCP is the smart kingdom. It excels at data, machine learning, and container orchestration (Google invented Kubernetes, after all). Its interfaces feel designed by engineers for engineers.

Azure is the enterprise kingdom — the one where all the big corporations already live. Microsoft spent decades selling Windows Server, Active Directory, SQL Server, and Office to every major company on earth. When those companies needed to move to the cloud, Azure was the natural choice. Azure speaks the language of the enterprise: compliance, hybrid cloud, .NET, and deep integration with Microsoft 365.

🏰 The Three Kingdoms

AWS: The giant market that has everything. Most developers start here. Most job postings mention it. The community is enormous.

GCP: The technical wizard's kingdom. Brilliant for Kubernetes, AI/ML, and analytics at scale. Runs on Google's global private fiber network.

Azure: The enterprise fortress. If your company runs Windows, Active Directory, and Office 365, Azure feels like home. Best for hybrid cloud (on-premises + cloud).

GCP — Google's Cloud

GCP launched in 2011 (five years after AWS) and has been catching up aggressively ever since. It is the second-largest cloud by market share. Its core infrastructure — the global network of undersea fiber cables, the custom-built servers, the Andromeda software-defined networking layer — is genuinely impressive engineering.

If you know AWS, GCP services will feel immediately familiar. Different names, same ideas. Here is the translation table:

GCP's Unique Strengths

  • GKE (Google Kubernetes Engine): Google literally invented Kubernetes and open-sourced it in 2014. Their managed Kubernetes is the most battle-tested on earth. Auto-upgrade, auto-repair, Autopilot mode (fully serverless Kubernetes where you pay per pod, not per node).
  • Cloud Run: deploy any container in seconds without thinking about Kubernetes, nodes, or clusters. It scales to zero (no traffic = zero cost), scales to thousands of instances under load, and you pay only per request. Probably the simplest path to production containers in all of cloud.
  • BigQuery: a serverless data warehouse that can query terabytes in seconds. Pay per query. No cluster to manage. The standard tool for analytics at scale.
  • Vertex AI: Google's managed ML platform. Train models, deploy them as endpoints, run AutoML. Tightly integrated with the same infrastructure that runs Google's own AI products.
  • Global Network: Google owns more undersea fiber cables than almost any private company. Traffic between your app and users anywhere in the world travels on Google's private network, not the public internet — lower latency, more reliability.
  • Firebase: real-time database, authentication, hosting, and push notifications for mobile and web apps. Acquired by Google and tightly integrated with GCP.

GCP CLI Basics

GCP's command-line interface is called gcloud. Install it from cloud.google.com/sdk. For storage, the separate gsutil command handles Cloud Storage buckets. 

# Authenticate with your Google account
gcloud auth login

# Set the active project
gcloud config set project my-project-id

# List active configuration
gcloud config list

# List all Compute Engine instances
gcloud compute instances list

# SSH into a VM (handles key exchange automatically)
gcloud compute ssh my-instance --zone=us-central1-a

# Create a VM
gcloud compute instances create my-server \
  --zone=us-central1-a \
  --machine-type=e2-medium \
  --image-family=ubuntu-2204-lts \
  --image-project=ubuntu-os-cloud \
  --boot-disk-size=20GB

# Upload to Cloud Storage
gsutil cp file.txt gs://my-bucket/
gsutil rsync -r ./dist gs://my-bucket/

# List objects in a bucket
gsutil ls gs://my-bucket/

# Make a bucket publicly readable (for static websites)
gsutil iam ch allUsers:objectViewer gs://my-bucket

Cloud Run — The Simplest Container Deployment

Cloud Run is remarkable. You give it a Docker container image. It deploys it, gives it a public HTTPS URL, automatically scales from zero to however many instances you need, and charges you only when requests are actively being processed. It handles SSL, load balancing, auto-scaling, and health checks — all automatically. For many applications, Cloud Run eliminates the need for Kubernetes entirely. 

# Method 1: Build with Cloud Build, deploy to Cloud Run
# (Cloud Build runs in GCP — no local Docker needed)
gcloud builds submit --tag gcr.io/my-project/myapp

# Deploy to Cloud Run (serverless containers)
gcloud run deploy myapp \
  --image gcr.io/my-project/myapp \
  --platform managed \
  --region us-central1 \
  --allow-unauthenticated \
  --port 3000 \
  --memory 512Mi \
  --cpu 1 \
  --max-instances 100 \
  --min-instances 0 \
  --set-env-vars NODE_ENV=production,LOG_LEVEL=info

# Method 2: Deploy directly from source code (no Dockerfile needed!)
# Cloud Run uses Buildpacks to automatically detect and build your app
gcloud run deploy myapp \
  --source . \
  --region us-central1 \
  --allow-unauthenticated

# View service details and URL
gcloud run services describe myapp --region us-central1

# View logs
gcloud logging read "resource.type=cloud_run_revision AND resource.labels.service_name=myapp" \
  --limit 50 --format json

# Rollback to a previous revision
gcloud run services update-traffic myapp \
  --region us-central1 \
  --to-revisions myapp-00003-abc=100

GKE — Managed Kubernetes

If you need full Kubernetes — multiple services, complex networking, stateful workloads — GKE is the gold standard. Its Autopilot mode means you define pods and GKE handles the underlying node infrastructure entirely. You don't think about EC2 equivalents at all. 

# Create a GKE Autopilot cluster (Google manages the nodes)
gcloud container clusters create-auto my-cluster \
  --region us-central1

# Get credentials so kubectl works with this cluster
gcloud container clusters get-credentials my-cluster \
  --region us-central1

# Now you can use kubectl normally
kubectl get nodes
kubectl get pods --all-namespaces

# Deploy your application
kubectl apply -f deployment.yaml
🤯 Fun Fact: GCP's Free Tier

GCP's free tier includes one e2-micro VM running 24/7 forever (not just 12 months like AWS), 5GB of Cloud Storage, 10GB of Cloud Logging per month, and the first 2 million Cloud Run requests per month. The always-free e2-micro is genuinely useful for running small hobby projects indefinitely.

Azure — Microsoft's Cloud Kingdom

Azure launched in 2010 and is now the second-largest cloud by revenue (neck and neck with GCP for second place). Its growth has been explosive — fueled largely by Microsoft's enormous enterprise customer base. Every company already running Windows Server, SQL Server, Active Directory, and Office 365 found Azure to be the natural cloud extension of their existing infrastructure.

Azure's service naming is... eclectic. Services have been renamed multiple times, some have been retired, and the organizational structure is less intuitive than AWS or GCP. But once you get past the naming, the services are comprehensive and often excellent for enterprise scenarios.

Azure's Unique Strengths

  • Azure Active Directory (now called Microsoft Entra ID): the gold standard for enterprise identity management. SSO, MFA, Conditional Access, seamless integration with Office 365 and thousands of third-party SaaS apps. If your company uses Microsoft 365, your identity system is already there.
  • Azure DevOps (formerly VSTS): a complete platform covering Boards (project management), Repos (Git), Pipelines (CI/CD), Test Plans, and Artifacts (package registry) — all integrated. Many enterprises use it as their entire engineering platform.
  • Hybrid Cloud: Azure Arc extends Azure management to on-premises servers and other clouds. Azure Stack brings Azure services to your own data center hardware. For enterprises that can't move everything to the cloud immediately, this is invaluable.
  • App Service: the most mature PaaS for deploying web apps. Native support for .NET, Node.js, Python, Java, PHP, Ruby. Deployment slots for zero-downtime blue/green deployments. Auto-scaling baked in.
  • Azure OpenAI Service: enterprise-grade access to OpenAI's GPT-4 and other models, with data privacy guarantees, compliance certifications, and VNet integration. The only place to get OpenAI models with Azure compliance.

Azure CLI Basics

Azure's CLI is called az. Install it from docs.microsoft.com/cli/azure/install-azure-cli. Resources in Azure are organized into Resource Groups — logical containers for related resources. Every resource belongs to exactly one resource group. 

# Login to Azure
az login
# Opens a browser for authentication

# List all subscriptions
az account list --output table

# Set the active subscription
az account set --subscription "My Subscription Name"

# Create a resource group (like an AWS account-level folder)
az group create \
  --name my-rg \
  --location eastus

# List all resource groups
az group list --output table

# Create a Virtual Machine
az vm create \
  --resource-group my-rg \
  --name my-server \
  --image Ubuntu2204 \
  --size Standard_B1s \
  --admin-username azureuser \
  --generate-ssh-keys \
  --public-ip-sku Standard

# SSH into the VM
az ssh vm \
  --resource-group my-rg \
  --name my-server

# Deploy a container instance (like ECS single-container)
az container create \
  --resource-group my-rg \
  --name myapp \
  --image myregistry.azurecr.io/myapp:latest \
  --ports 3000 \
  --cpu 1 \
  --memory 1 \
  --registry-login-server myregistry.azurecr.io \
  --registry-username myuser \
  --registry-password $ACR_PASSWORD \
  --dns-name-label myapp-unique-dns

Azure App Service — The Simplest App Deployment

For web applications, Azure App Service is Azure's equivalent of a managed PaaS platform. You define a plan (the compute tier) and a web app (your application), and Azure handles the underlying OS, patching, scaling, and availability. It supports deployment from GitHub, Azure DevOps, Docker containers, or local Git pushes. 

# Step 1: Create an App Service Plan (defines compute tier and OS)
az appservice plan create \
  --name my-plan \
  --resource-group my-rg \
  --sku B1 \
  --is-linux
# SKUs: F1 (free), B1 (basic $13/mo), S1 (standard, autoscale), P1v3 (premium)

# Step 2: Create the Web App
az webapp create \
  --resource-group my-rg \
  --plan my-plan \
  --name my-unique-app-name \
  --runtime "NODE:20-lts"
# Other runtimes: "PYTHON:3.11", "DOTNETCORE:8.0", "JAVA:17-java17"

# Step 3: Deploy from a local directory
az webapp up \
  --name my-unique-app-name \
  --resource-group my-rg \
  --runtime "NODE:20-lts"

# Or: Deploy from GitHub with continuous deployment
az webapp deployment source config \
  --name my-unique-app-name \
  --resource-group my-rg \
  --repo-url https://github.com/myorg/myapp \
  --branch main \
  --manual-integration

# Set environment variables (like Heroku config vars)
az webapp config appsettings set \
  --name my-unique-app-name \
  --resource-group my-rg \
  --settings DATABASE_URL="postgresql://..." NODE_ENV="production"

# Scale the app to 3 instances
az appservice plan update \
  --name my-plan \
  --resource-group my-rg \
  --number-of-workers 3

# Stream live logs
az webapp log tail \
  --name my-unique-app-name \
  --resource-group my-rg

Azure Container Apps — The Cloud Run Equivalent

Azure Container Apps is Microsoft's answer to Cloud Run: serverless containers that scale to zero, pay per request, no Kubernetes to manage. It is built on Kubernetes under the hood but abstracts it completely. 

# Create a Container Apps environment
az containerapp env create \
  --name my-env \
  --resource-group my-rg \
  --location eastus

# Deploy a container app
az containerapp create \
  --name myapp \
  --resource-group my-rg \
  --environment my-env \
  --image myregistry.azurecr.io/myapp:latest \
  --target-port 3000 \
  --ingress external \
  --min-replicas 0 \
  --max-replicas 10 \
  --cpu 0.5 \
  --memory 1Gi

How to Choose Your Cloud

This is one of the most common questions developers ask, and the honest answer is: for most projects, any of the three will work. The differences at small-to-medium scale are largely cosmetic. At large scale, the differences start to matter.

Here is a practical decision framework: 

Cloud Selection Decision Tree
──────────────────────────────────────────────────────────────────

Does your company use Microsoft 365 / Active Directory?
  └── YES → Start with Azure. AAD integration alone is worth it.
  └── NO ↓

Is Kubernetes a core part of your platform?
  └── YES → Consider GCP (GKE is best-in-class) or AWS (EKS)
  └── NO ↓

Do you have heavy AI/ML or analytics requirements?
  └── YES → GCP (BigQuery, Vertex AI are exceptional)
  └── NO ↓

Do you want the biggest community, most third-party integrations,
and best job market demand?
  └── YES → AWS

Is simplicity your top priority and you just want to run containers?
  └── YES → GCP Cloud Run or Azure Container Apps

Are you starting from scratch and don't know which to pick?
  └── Pick AWS. Learn it deeply. Transfer knowledge later.

──────────────────────────────────────────────────────────────────
Quick Reference by Use Case:

Kubernetes-heavy platform      → GKE (GCP) then EKS (AWS)
Serverless containers          → Cloud Run (GCP) or App Service (Azure)
Microsoft/.NET applications    → Azure App Service
Machine learning / AI          → Vertex AI (GCP) or SageMaker (AWS)
Data warehouse / analytics     → BigQuery (GCP) or Redshift (AWS)
Enterprise SSO / Active Dir.   → Azure Entra ID
Maximum service variety        → AWS
Maximum simplicity             → Cloud Run (GCP)
💡 Tip: Learn AWS First

The cloud concepts transfer completely between providers. IAM on AWS, IAM on GCP, and RBAC on Azure all solve the same problem with slightly different JSON. VPCs on AWS are VPCs on GCP and VNets on Azure. S3 buckets are Cloud Storage buckets are Blob Storage containers. Master the concepts on AWS — it has the most learning resources, tutorials, and Stack Overflow answers — then translate to GCP or Azure in a day.

Multi-Cloud Reality

Walk into any large technology company — a bank, a retailer, a media company — and you will almost certainly find services running on multiple cloud providers simultaneously. This is not because their engineers enjoy complexity. It happens for several practical reasons:

  • Acquisitions: company A (on AWS) acquires company B (on GCP). Now you have both.
  • Best-of-breed services: BigQuery is so much better for analytics that companies running primarily on AWS use it anyway. Azure OpenAI has compliance guarantees that AWS Bedrock doesn't match yet.
  • Negotiation leverage: spending with multiple clouds gives you bargaining power on pricing.
  • Risk mitigation: major cloud outages happen (AWS us-east-1 going down makes news). Running critical services across providers reduces single-provider risk.

Managing multiple clouds sounds terrifying, but tools like Terraform (covered in Part 4) abstract the provider differences. You write infrastructure in one language and Terraform talks to AWS, GCP, and Azure APIs on your behalf. The mental overhead is the naming conventions, not the underlying infrastructure concepts.

🤯 Fun Fact: Cloud Market Share

As of 2024, AWS holds approximately 31% of the global cloud infrastructure market, Azure holds 25%, and GCP holds 11%. The remaining 33% is split among hundreds of smaller providers. AWS's lead has gradually narrowed as Azure and GCP have matured, but AWS remains the default choice for new projects across the industry.

Chapter Summary

  • AWS is the biggest and most versatile cloud; GCP excels at Kubernetes, AI, and analytics; Azure dominates enterprise Microsoft environments.
  • GCP's Cloud Run is the simplest path to production containers — deploy any Docker image, scales to zero, pay per request.
  • GKE (Google Kubernetes Engine) is the most mature managed Kubernetes service, built by the team that invented Kubernetes.
  • Azure's greatest strength is enterprise identity management via Entra ID (formerly Active Directory), and .NET application hosting via App Service.
  • Azure Container Apps mirrors GCP Cloud Run — serverless containers without managing Kubernetes clusters.
  • Choose cloud based on your existing stack and requirements; learn AWS first, the concepts transfer to all three.
  • Multi-cloud is common at scale — use Terraform to manage infrastructure consistently across providers.
