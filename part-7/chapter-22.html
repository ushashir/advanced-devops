Developer Platforms

You've learned to build pipelines, deploy containers, and secure secrets. Now learn to build the platform that lets your entire organisation do all of that without needing your help every day.

The Airport Analogy
Imagine your engineering org is an airport. Individual developers are passengers — they just want to get from A to B (idea to production). Without a platform, every passenger has to navigate a jungle: find their own plane, file their own flight plan, refuel the engine, and hope they land safely.

A developer platform is the airport itself. Clear terminals, departure boards, security lanes, moving walkways. The passenger just shows up with a ticket and flies. The airport (your platform team) handles everything else behind the scenes. Backstage is the departure board and terminal map. Crossplane is the automated ground crew that provisions aircraft, fuel, and gates on demand.

What is Platform Engineering?

Platform Engineering is the discipline of building internal tools and infrastructure that make other engineers more productive. Instead of every team figuring out how to deploy to Kubernetes, set up monitoring, or provision a database, the platform team builds a paved road — one well-lit, well-tested path that anyone can walk.

Internal Developer Platform (IDP) — a self-service layer that abstracts away infrastructure complexity. Developers interact with the platform through simple interfaces (a UI, a CLI, or a Git PR) and the platform handles provisioning, security, compliance, and deployment underneath.

The goal is to reduce cognitive load. A backend engineer should not need to know the difference between a Kubernetes NodePort and a LoadBalancer just to ship a feature. That knowledge belongs in the platform, not in every engineer's head.

Backstage: The Software Catalog

Backstage is an open-source framework from Spotify for building developer portals. Think of it as the home page for your entire engineering organisation — a single place where developers can find every service, every API, every pipeline, and every piece of documentation.

The Software Catalog

The Catalog is Backstage's core feature. Every service, library, website, and data pipeline in your org is registered as an Entity described by a YAML file called a catalog-info.yaml.

# catalog-info.yaml — lives in the root of every service repo
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: payment-service
  description: Handles payment processing for all orders
  annotations:
    github.com/project-slug: myorg/payment-service
    backstage.io/techdocs-ref: dir:.
  tags:
    - java
    - payments
    - critical
spec:
  type: service
  lifecycle: production
  owner: payments-team
  system: checkout-platform
  dependsOn:
    - component:order-service
    - resource:payments-database

Backstage reads this file from your repo and populates the catalog automatically. Now any engineer can open the portal and see: what services exist, who owns them, what they depend on, their current health, links to their Grafana dashboards, CI/CD status, and API documentation — all in one place.

Installing Backstage

# Prerequisites: Node.js 18+, Yarn
npx @backstage/create-app@latest

# Follow the prompts — choose SQLite for local dev, PostgreSQL for production
# This creates a full Backstage app in a new directory

cd my-backstage-app
yarn dev
# Opens at http://localhost:3000

Software Templates

Templates are Backstage's killer feature for platform teams. Instead of copy-pasting boilerplate from an old repo, developers open Backstage, pick a template ("Create a new Node.js microservice"), fill out a form (name, owner, database needed?), and Backstage automatically:

  • Creates a new GitHub repo with the correct folder structure
  • Generates the Dockerfile, kubernetes/ manifests, and catalog-info.yaml
  • Sets up GitHub Actions CI/CD
  • Registers the new service in the catalog
  • Creates a Grafana dashboard
# template.yaml — a Backstage Software Template
apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name: nodejs-microservice
  title: Node.js Microservice
  description: Creates a production-ready Node.js service with CI/CD
  tags:
    - nodejs
    - microservice
spec:
  owner: platform-team
  type: service

  parameters:
    - title: Service Details
      required:
        - name
        - owner
      properties:
        name:
          title: Service Name
          type: string
          description: Unique name for your service (kebab-case)
        owner:
          title: Owner Team
          type: string
          ui:field: OwnerPicker
          ui:options:
            allowedKinds:
              - Group
        needsDatabase:
          title: Needs a PostgreSQL database?
          type: boolean
          default: false

  steps:
    - id: fetch-template
      name: Fetch Template
      action: fetch:template
      input:
        url: ./skeleton
        values:
          name: ${{ parameters.name }}
          owner: ${{ parameters.owner }}
          needsDatabase: ${{ parameters.needsDatabase }}

    - id: create-repo
      name: Create GitHub Repository
      action: publish:github
      input:
        repoUrl: github.com?repo=${{ parameters.name }}&owner=myorg
        defaultBranch: main

    - id: register
      name: Register in Catalog
      action: catalog:register
      input:
        repoContentsUrl: ${{ steps['create-repo'].output.repoContentsUrl }}
        catalogInfoPath: /catalog-info.yaml
Why Templates Matter
Before templates, a new service at Spotify took days of setup — copying configs, figuring out CI, setting up monitoring. With Backstage Templates, the same setup takes five minutes. Every new service starts golden: with tests, security scanning, observability, and documentation built in from day one.

TechDocs

TechDocs is Backstage's documentation system. Engineers write docs as Markdown files alongside their code (in a docs/ folder), and Backstage renders them as a searchable, versioned documentation site. No more hunting for the right Confluence page — everything is in the catalog next to the service that owns it.

# mkdocs.yml — at the root of your service repo
site_name: Payment Service
nav:
  - Home: index.md
  - Architecture: architecture.md
  - API Reference: api.md
  - Runbooks: runbooks.md
docs_dir: docs

Crossplane: Kubernetes as a Cloud Control Plane

Crossplane is an open-source Kubernetes add-on that lets you provision and manage cloud infrastructure — AWS RDS databases, GCP buckets, Azure Redis caches — using Kubernetes manifests, the same way you manage Deployments and Services.

The Hotel Concierge Analogy
Normally, if you need a database, you go to the AWS console, click through eight screens, wait 15 minutes, copy the connection string, and paste it into a Secret manually. With Crossplane, your developer writes a Kubernetes YAML that says "I need a PostgreSQL database, please." Crossplane is the concierge — it takes that YAML, calls AWS on your behalf, provisions the RDS instance, and drops the connection secret directly into your namespace. The developer never touches the AWS console.

Installing Crossplane

# Install Crossplane into your Kubernetes cluster
helm repo add crossplane-stable https://charts.crossplane.io/stable
helm repo update

helm install crossplane \
  --namespace crossplane-system \
  --create-namespace \
  crossplane-stable/crossplane

# Install the AWS provider
kubectl apply -f - <

Managed Resources

A Managed Resource is a Crossplane object that maps 1:1 to a real cloud resource. When you create a RDSInstance in Kubernetes, Crossplane calls the AWS API and creates an actual RDS database.

# rds-instance.yaml — provisions a real AWS RDS PostgreSQL database
apiVersion: rds.aws.upbound.io/v1beta1
kind: Instance
metadata:
  name: orders-db
  namespace: production
spec:
  forProvider:
    region: us-east-1
    dbInstanceClass: db.t3.micro
    engine: postgres
    engineVersion: "14"
    allocatedStorage: 20
    dbName: orders
    username: admin
    skipFinalSnapshot: true
    publiclyAccessible: false
  writeConnectionSecretsToRef:
    namespace: production
    name: orders-db-connection  # Crossplane writes credentials here
# Apply it like any Kubernetes resource
kubectl apply -f rds-instance.yaml

# Watch Crossplane provision the database
kubectl get instance orders-db -n production -w

# NAME        READY   SYNCED   EXTERNAL-NAME                    AGE
# orders-db   False   True     orders-db-xyz123.us-east-1.rds   30s
# orders-db   True    True     orders-db-xyz123.us-east-1.rds   4m

# The connection string is now a Kubernetes Secret
kubectl get secret orders-db-connection -n production -o yaml

Compositions: Building Your Own Abstractions

Raw Managed Resources expose every AWS option, which is overwhelming for developers. Compositions let the platform team create higher-level abstractions — a PostgreSQLDatabase that automatically includes the right instance size, backup retention, security groups, and monitoring, without the developer needing to know any of that.

# composite-resource-definition.yaml — defines a custom resource type
apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: xpostgresqldatabases.platform.mycompany.com
spec:
  group: platform.mycompany.com
  names:
    kind: XPostgreSQLDatabase
    plural: xpostgresqldatabases
  claimNames:
    kind: PostgreSQLDatabase    # This is what developers use
    plural: postgresqldatabases
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                size:
                  type: string
                  enum: [small, medium, large]  # Simple choice, no AWS jargon
                region:
                  type: string
                  default: us-east-1
# composition.yaml — maps the simple spec to real AWS resources
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: postgresql-aws
spec:
  compositeTypeRef:
    apiVersion: platform.mycompany.com/v1alpha1
    kind: XPostgreSQLDatabase
  resources:
    - name: rds-instance
      base:
        apiVersion: rds.aws.upbound.io/v1beta1
        kind: Instance
        spec:
          forProvider:
            engine: postgres
            engineVersion: "14"
            skipFinalSnapshot: true
      patches:
        - fromFieldPath: spec.region
          toFieldPath: spec.forProvider.region
        - fromFieldPath: spec.size
          toFieldPath: spec.forProvider.dbInstanceClass
          transforms:
            - type: map
              map:
                small: db.t3.micro
                medium: db.t3.medium
                large: db.r6g.large

Now a developer can claim a database with a five-line YAML — no AWS knowledge required:

# my-app-database.yaml — written by the application developer
apiVersion: platform.mycompany.com/v1alpha1
kind: PostgreSQLDatabase
metadata:
  name: my-app-db
  namespace: my-team
spec:
  size: small
  region: us-east-1
  writeConnectionSecretToRef:
    name: my-app-db-credentials

Putting It All Together: The Golden Path

The golden path is the platform engineering term for the happy path — the well-paved route through your infrastructure that you've made so easy that developers naturally use it.

Developer opens Backstage
         │
         ▼
  Picks "New Microservice" Template
         │
         ▼
  Fills in: name, team, "needs database? yes"
         │
         ▼
  Backstage scaffolds:
  ├── GitHub repo with Node.js boilerplate
  ├── Dockerfile + Kubernetes manifests
  ├── GitHub Actions pipeline
  ├── catalog-info.yaml
  └── PostgreSQLDatabase claim (Crossplane)
         │
         ▼
  ArgoCD detects the new repo → deploys to staging
         │
         ▼
  Crossplane sees the claim → provisions RDS database
  └── Injects credentials as a Kubernetes Secret
         │
         ▼
  Developer pushes first feature → pipeline runs:
  tests → security scan → build image → deploy
         │
         ▼
  Grafana dashboard auto-created
  Backstage catalog shows service health
  TechDocs renders README as documentation

The developer wrote a feature. They never touched AWS, Kubernetes YAML, GitHub Actions setup, Prometheus configuration, or Vault. The platform handled all of it. That's the dream.

Platform Team as Product Team
The best platform teams treat their internal developers as customers. They run user research, gather feedback, measure time-to-first-deploy for new engineers, and iterate on their tools the same way product teams iterate on user-facing features. If developers are bypassing the platform and doing things manually, that's a bug — not a discipline problem.

Chapter Summary

  • Platform Engineering builds internal tools that reduce cognitive load for developers — the goal is self-service infrastructure.
  • Backstage is an open-source developer portal. Its core features are the Software Catalog (every service in one place), Software Templates (automated service scaffolding), and TechDocs (docs-as-code).
  • Crossplane turns Kubernetes into a universal control plane. It provisions cloud resources (RDS, S3, Redis) via Kubernetes manifests, and Compositions let you build simple abstractions over complex AWS primitives.
  • The golden path combines all these tools: a developer picks a template, Backstage scaffolds a repo, ArgoCD deploys it, and Crossplane provisions its dependencies — all without the developer needing deep infrastructure knowledge.
